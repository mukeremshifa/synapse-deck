# P10 — Document ingestion, on AWS

Phase B of [AWS-NATIVE-BRIEF.md](AWS-NATIVE-BRIEF.md). The phase that makes the pipeline
AWS-native: S3 upload, Step Functions fan-out over chunks, Bedrock generation, DynamoDB
job state — and it ends the SSE stream that P2 built.

**Reference:** the brief's D3, D5, D6, D10, §6 cost controls 1–3, §7 open questions 1, 2,
3, 4, 6, 7, §8 constraints 1, 3, 8, 10. P9's [ADR 0008](../adr/0008-application-level-tenancy.md)
governs every new table and every new data-access module; it is not reopened here.

**Done when:** a user drops a PDF on `/create/document`, watches honest progress, and ends
at the review gate with cards generated by Bedrock — and `/create/text` still works,
having moved to the same pipeline rather than keeping a second one.

## What P9 leaves you, stated plainly

Read this before the tasks; several of them exist only because of it.

**P9 built the whole API and never ran it.** Four data modules, five Lambdas, 18 routes,
a schema, three RPCs — typechecked, synthesised, and never once executed against a
database. `npm run verify` was green throughout and proves only that it compiles.

**So P10's task 1 is not "deploy P9's stacks", it is "find out what P9 got wrong."** Budget
a session for it and expect real bugs: a column name that does not match, a `pg` type
parser that returns the wrong shape, a route that 404s because the path matcher reads
`endsWith`. That is a normal outcome for code that has never run, not a sign the phase was
done badly.

Specifically inherited, and specifically unproven:

| Thing | Where | What is unknown |
| ----- | ----- | --------------- |
| The schema | `services/api/migrations/0001_schema.sql` | Never executed anywhere |
| `review_card` / `undo_last_review` | `0002_review_card.sql` | Never called; the `p_user_id` filters are untested |
| The data layer | `services/api/src/data/` | Never issued a query |
| The row types | `services/api/src/lib/rows.ts` | Hand-transcribed; agree with the client's generated types by assertion only |
| Cognito sign-in | `src/lib/cognito.ts` | Never authenticated anybody |
| Cold start in a VPC | — | Still unmeasured (P9 task 2 asked for the number) |

**And one thing P9 could not do at all:** `npm run demo:seed` is broken by the split — its
value is driving the real generation pipeline, which writes into Supabase, while decks and
cards moved to RDS. **P10 is the phase that fixes it**, because P10 is where generation
moves. See task 11.

## Tasks

Ordered so the app runs after every one.

### 1. Deploy P9, and debug what has never run

**This is the whole first session and it is not a formality.**

- `npm run infra:diff` and read every line. Four new dev stacks; the Data stack is where
  the money starts.
- `npm run infra:deploy`. Expect the budget alarms to fire, correctly.
- Invoke the migration Lambda with `{"statusOnly": true}` **first** — it is this project's
  `db push --dry-run`, and `CLAUDE.md` requires that step. Read what it lists, then run it
  for real.
- Sign up through the app's own screens. That is task 1's real acceptance: the first
  Cognito account, created the way a user would.
- **Then exercise every route by hand** — create a deck, add a card, practise, rate, undo.
  Each one is a first execution.

**Two measurements to write down, both of which P9 owes:**

1. **Lambda-in-VPC cold start.** P9 task 2 requires the number and could not take it.
   Write it into `docs/plans/P9-aws-slice.md` task 2, replacing the paragraph that says it
   is unmeasured, and into this plan if it changes any decision below.
2. **The cross-tenant check** (P9 acceptance criterion 5). Two accounts; B calls
   `GET /decks/{a-deck-id}` with A's id and a valid B token; expect **404, not 403**.
   Repeat for a card and a review. Record the output in P9's plan. **This is the only
   evidence that will ever exist that ADR 0008's boundary holds** — the test that used to
   prove it was deleted, and the lint checks shape rather than meaning.

Fix what is broken. Commit the fixes separately from the deploy, so the diff between "what
P9 wrote" and "what actually works" is readable — that difference is the honest artifact of
building without a test suite, and it is worth being able to point at.

### 2. Job state in DynamoDB — `infra/lib/pipeline-stack.ts`

D3's other half. One table, single-table design, on-demand billing (free at idle, and this
is idle almost always).

- Partition key `userId`, sort key `jobId#…`. **`userId` is the partition key deliberately**
  — it makes the tenancy boundary a property of the key rather than a filter, which is a
  genuinely stronger position than the SQL side has (ADR 0008 admits as much). Do not model
  it any other way for convenience.
- TTL on job records. Pipeline state is not history: a finished job is interesting for
  hours, not months, and a TTL is what stops this table becoming a second database nobody
  meant to keep.
- **A data-access module, under the same four rules.** `services/api/src/data/jobs.ts`,
  `userId` first, required. `scripts/check-data-access.mjs` enforces rules 1 and 3 whether
  the store is Postgres or DynamoDB — its checks are about the shape of the function, and a
  DynamoDB call in a handler is exactly as wrong as SQL in one. **Extend the lint's
  patterns to catch `DynamoDBClient` / `send(` in a handler** rather than leaving a gap it
  was never taught about.
- **DynamoDB needs a VPC endpoint** — a *gateway* endpoint, which is free, exactly like
  S3's. Add it to the Data stack. Without it the SDK call from a VPC Lambda hangs until it
  times out, which presents as a mysteriously slow function rather than a connection error
  (`infra/lib/data-stack.ts` already warns about this trap).

### 3. Upload — S3, presigned, and the scanned-PDF check

§7 question 6, and the browser half is worth more than any server-side cleverness.

- Presigned PUT from a small Lambda; the browser uploads directly to S3. The file never
  passes through the API, which is what keeps a 20 MB PDF off a Lambda's memory.
- Object key prefixed by `userId` (D4: *"`sub` becomes `userId` everywhere — S3 object
  prefixes"*), so the bucket policy can scope access by prefix and the boundary is visible
  in the key.
- **Detect a missing text layer in the browser, before the upload.** Parse the first page
  or two client-side; if there is no extractable text, say so *then* — "this looks like a
  scan; text extraction will not work on it" — rather than after a 20 MB upload and a
  failed pipeline. That is the answer to §7 question 6 and it is a product decision as much
  as a technical one.
- No OCR. Say so in the copy. Textract is a real answer and it is out of scope for this
  phase; do not add it because it is tempting.
- Lifecycle rule: delete uploads after N days. The source document is an input, not an
  archive, and S3 is only free to 5 GB.

### 4. The draft-card seam — §7 question 4

**Settle this before writing the state machine**, because it decides what every chunk task
returns.

The brief says drafts live in DynamoDB and acceptance writes to Postgres. That is one
audited write path, and the whole question is where the boundary sits:

- Chunks write draft cards into DynamoDB, keyed by job. Nothing touches Postgres during
  generation, so a failed job leaves no half-written deck.
- **Acceptance is one API call** that reads the job's drafts, validates every payload with
  the shared `CardPayload` schema, and inserts into `cards` in one transaction. One path,
  in `services/api/src/data/`, under the four rules.
- The review gate reads drafts from DynamoDB, not from `cards`. **This changes
  `useDraftCards`**, which P9 pointed at `GET /decks/{id}/cards?status=draft`. Decide
  whether `cards.status = 'draft'` still means anything after this phase — if drafts never
  reach Postgres before acceptance, that enum value is dead and should be either removed
  or documented as legacy in the same commit.

Write the answer into `SPEC.md`, not only into code: it is a change to what a "draft" is.

### 5. Step Functions, and the end of SSE — §7 question 2

D5. Map state over chunks, per-chunk retry, partial failure as a normal outcome.

- **Job-status polling replaces the SSE stream.** The brief calls this "boring and probably
  correct"; it is also the only option that survives a Lambda that cannot hold a connection
  for the length of a fan-out. `GET /jobs/{jobId}` returns status, per-chunk progress and a
  card count.
- Poll interval that backs off. A job takes tens of seconds; polling every 500 ms for the
  whole of it is a cost and a rate limit for no extra information.
- **`src/lib/sse.ts` and `src/lib/ndjson.ts` become dead code** when `/create/text` moves
  (task 9). Delete them in that commit rather than leaving two decoders nobody calls —
  `supabase/functions/_shared/ingest.ts` re-exports them, so this is coordinated with
  retiring the Edge Function's use of them, not before.

### 6. Partial failure, in the UI — §7 question 3

"31 of 40 chunks produced cards; 9 failed" is the normal case, not the exception, and the
brief says so.

- The job record carries per-chunk status. The UI says how many chunks failed and offers
  the cards that did arrive — a fan-out that discards 31 good chunks because 9 failed is
  worse than one that admits the gap.
- Retry is per chunk, in the state machine, before the user ever sees a failure. What
  reaches the UI is what failed *after* retries.
- **Do not hide it.** A deck that quietly contains three quarters of a document is a
  product that lies. One line at the review gate.

### 7. Where topics come from — §7 question 7

**D11 depends on this and Phase C cannot start without it**, which is why it is here rather
than in Phase C.

The failure mode is specific: a user studying one subject across five uploads must not get
five overlapping topic sets, or the mastery map is meaningless.

- Extract topics per document with the model, then **reconcile against the user's existing
  topics** rather than creating fresh ones. The reconciliation is the actual work; the
  extraction is easy.
- Reconcile by name first — cheap, and catches the common case. Anything ambiguous is where
  Phase G's pgvector would help; **do not build embeddings here**, and say in the ADR that
  the phase knowingly accepted a weaker match to avoid pulling Phase G forward.
- `topics` is a new table, so: `user_id not null`, indexed, **and a data-access module with
  all four rules on the day it is created**. A new table on RDS without one is a
  cross-tenant leak, not a TODO (`CLAUDE.md`).
- **This deserves an ADR** — the brief's D11 anticipated one "if the planning session finds
  the schema contentious", and topic stability is exactly the contentious part.

### 8. Quota for multi-chunk work — §7 question 1

A *product* decision, and the brief says so. Today: 30 generations a month, one card
generation = one unit.

- Decide what a document costs. "One document = 12 units" is the brief's own illustration,
  not a decision.
- **Charge by work done, not by button press.** A 3-page PDF and a 300-page textbook are
  not the same unit, and a quota that says they are is one a user will find unfair the
  first time it matters.
- The quota must be **checkable before the job starts** — refusing at chunk 30 of 40, after
  spending the money, is the worst version of this.
- `generations` currently lives on Supabase and is read by `useQuotaUsage`. **This phase
  moves it**, because this phase is what writes it. That is the split table's own schedule
  (`generations` + quota → Phase B), so update the table in
  [P9-aws-slice.md](P9-aws-slice.md) when it moves rather than leaving it stale.

### 9. `/create/text` moves to the same pipeline

§8 constraint 8: no feature is built twice.

- The text path becomes a one-chunk job through the same state machine. Not a second code
  path with a shared schema — the *same* path.
- **The Edge Function stops being called.** Leave it deployed until Phase F (it is what
  `/progress`-era code still expects), but nothing in the app invokes it after this task.
- `GROQ_API_KEY` stays as the fallback provider behind D6's interface, now called from
  Lambda rather than from Deno.

### 10. Bedrock, behind the interface D6 describes

- One provider interface, two implementations, sharing the Zod schemas at the boundary
  that `src/lib/schemas.ts` already is. That sharing is the existing pattern
  (`services/api/src/lib/schemas.ts` re-exports for exactly this reason) — follow it.
- Haiku-class for routine generation. Larger models only behind an explicit action.
- **The three cost controls from §6 are constraints, not advice** (§8 constraint 10):
  cap the work per call, cache blueprints by document version + settings, and generate
  explanations on demand. Two of the three belong to Phase C, but **the caching seam is
  built here** or Phase C retrofits it.
- Token and cost accounting per job, into DynamoDB (D3 puts it there). This is what makes
  "$0.45 per full loop" a measured number rather than an estimate — and the eval harness
  D6 calls "the valuable artifact" needs it.

### 11. Fix `demo:seed`

P9 broke it and could not fix it; this is the phase where it becomes fixable, because
generation now writes into RDS.

- Point it at the new API and Cognito. `adminUserPassword` is enabled on the app client

- **Keep rule 2**: it drives the real pipeline. That is the entire reason the script exists
  rather than a fixture file, and it is now achievable again.
- **Keep rule 3**: the review history is replayed through `applyGrade`, not invented. That
  half is backend-agnostic and is the hard part; do not rewrite it.
- Restore P9's dropped acceptance criterion 2 as this phase's: `demo:seed` builds the demo
  account against the new API and its decks are visible when signed in as that account.

## Acceptance criteria

1. A PDF dropped on `/create/document` produces cards, through S3 → Step Functions →
   Bedrock → DynamoDB → the review gate.
2. A scanned PDF is refused **in the browser**, before the upload, with copy that says why.
3. A job with failed chunks shows what failed and still offers the cards that succeeded.
4. `/create/text` runs through the same state machine. Nothing calls the Edge Function.
5. `npm run demo:seed` builds the demo account against the new API and its decks are
   visible when signed in as that account.
6. Topics extracted from two documents on the same subject **reconcile into one set**, not
   two. Checked by hand with two real documents, and the output recorded here.
7. The cross-tenant check from task 1 is recorded, in `P9-aws-slice.md`, with its output.
8. Lambda-in-VPC cold start is measured and written into P9 task 2.
9. `npm run verify` is green, including the data-access lint extended to DynamoDB.
10. Still no NAT Gateway. `aws ec2 describe-nat-gateways` returns empty.
11. `/progress` still says it is showing pre-migration data — it is still true after this
    phase, and the sentence is only removed in Phase F.

## What went unverified

Fill this in as the phase runs; these are the ones already predictable:
